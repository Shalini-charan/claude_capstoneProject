Agentic SDLC Pipeline — Agent Overview

A set of Claude Code agents that take a Jira ticket (or a feature description) and drive it through requirements, design, implementation, review, testing and a pull request. Start it with the /run-orchestrator slash command.

Pipeline at a glance

1 Requirements→ 2 Architecture→ 3 Design Review→ 4 Impl Plan→ 5 Implementation→ 6 Code Review→ 7 Verify→ 8 Pull Request

Orange outline = quality gate (pipeline pauses and asks "Approve and continue? yes / revise"). Other stages run automatically unless an error occurs.

Orchestrator

sdlc-orchestrator

Master agent

Runs the whole pipeline from one prompt by invoking each specialist agent in order, enforcing quality gates and keeping the developer informed with a progress board.

Tools
Read, Write, Edit, Bash, Glob, Grep, Agent
Input
A Jira ticket ID (e.g. CLAUDE-1) or a feature description.
Does
  • Prints an 8-stage status board (PENDING / IN PROGRESS / DONE) and reprints it after every stage.
  • Skips a stage if its output document already exists, and can resume a paused pipeline from the files present.
  • Verifies each output file exists and is non-empty, then summarises it.
  • Implements the plan itself (Stage 5) and writes and runs the tests (Stage 7).
  • Applies fixes for CRITICAL/HIGH code review findings before moving on.
Output
All stage documents, the implemented code and tests, and finally the PR URL.
On error
Re-invokes an agent once if it returns empty output; does not reach Stage 8 with failing tests; reports exact git/gh errors and asks how to proceed.

Specialist agents

1. requirements-agent

Stage 1Approval gate

Acts as a senior business analyst and turns a ticket or feature description into structured requirements.

Tools
Read, Write, Glob
Input
Jira ticket (via MCP) or a user description. Asks one clarifying question at a time if something is ambiguous.
Does
Writes atomic, testable Functional Requirements (FR-N), Non-Functional Requirements (NFR-N) and Constraints (C-N, each labelled FIXED or ASSUMED). Does not invent requirements.
Output
docs/requirements.md with FR, NFR and Constraints tables.

2. architecture-agent

Stage 2Automatic

Acts as a principal architect and designs the simplest system that meets the requirements.

Tools
Read, Write, Glob
Input
docs/requirements.md
Does
Defines components with their responsibility and public interface, numbered data flow, key data structures, Architecture Decision Records (DD-NN) and Known Limitations (KL-N). Prefers stdlib, and validates each component against at least one functional requirement.
Output
docs/architecture.md

3. design-review-agent

Stage 3Approval gate

Acts as a senior staff engineer running an adversarial review to find problems before code exists.

Tools
Read, Write, Glob
Input
docs/architecture.md and docs/requirements.md
Does
Checks correctness, reliability, portability, security and completeness. Records each risk as RISK-NN with severity (HIGH/MEDIUM/LOW), component, scenario, mitigation and status (OPEN/ACCEPTED/FIXED). Every HIGH risk needs a concrete mitigation.
Output
docs/design-review.md (risk register). Open HIGH/CRITICAL risks block Stage 4.

4. impl-plan-agent

Stage 4Approval gate

Acts as a tech lead and turns the approved design into an actionable plan.

Tools
Read, Write, Glob
Input
docs/architecture.md and docs/design-review.md
Does
Groups work into phases and atomic tasks (T-NN) with dependencies, and marks which tasks can run in parallel. Every FIXED risk gets an implementation task, and tests are explicit tasks.
Output
docs/impl-plan.md with a task table and a "Parallel Groups" section.

5. Implementation (orchestrator)

Stage 5Automatic

No separate agent. The orchestrator works through the plan in dependency order.

Does
For each task: announces it, writes or edits the listed files, runs a quick sanity check (e.g. an import). Stops and reports if any task fails.
Output
All src/ files listed in the plan.

6. code-review-agent

Stage 6Automatic

Acts as a senior engineer doing a pre-merge review. It is read-only and reports only findings that have a concrete scenario.

Tools
Read, Glob, Grep
Input
Source files listed in docs/impl-plan.md (or everything under src/).
Does
Reviews correctness, security, reliability and clarity. Each finding (FIND-NN) has file:line, severity, category, issue, scenario and exact fix. CRITICAL and HIGH block merge; MEDIUM and LOW are advisory.
Output
Findings report ending with N findings (C critical, H high, M medium, L low).

7. Verify (orchestrator)

Stage 7Automatic

No separate agent. The orchestrator writes and runs the tests.

Does
Writes tests/test_<module>.py (unit + integration), runs python -m unittest discover -s tests -v, and fixes failures. All tests must pass before Stage 8.
Output
Passing test run.

8. pr-agent

Stage 8Automatic

Acts as a tech lead writing a pull request that reviewers can approve with confidence.

Tools
Read, Glob, Bash
Input
Requirements, architecture, design review, impl plan and git log --oneline.
Does
Writes the PR body: Summary, Changes Made (file table), How to Test, Test Evidence, Known Limitations (each tied to its KL-N), and a Reviewer Checklist with one item per functional requirement. The orchestrator creates the feature branch, pushes it and opens the PR.
Output
docs/pr-description.md and the GitHub PR URL.

Integrations (MCP)

The atlassian and github MCP servers are configured in .mcp.json. When connected, the pipeline uses them as below; otherwise it falls back to local files and the gh CLI.

StageIntegration
1Pulls the Jira issue (summary, description, acceptance criteria, labels, priority); comments on the ticket once requirements are approved.
2–4Publishes architecture, design review and impl plan to the Confluence space CLAUDE.
6Posts a code review summary (counts by severity) as a Jira comment.
8Creates the GitHub PR, transitions the Jira ticket to "In Review" and comments with the PR URL.

Slash commands

CommandWhat it does

/design-archRuns the architecture step on its own.
/review-codeRuns the code review step on its own.

Hooks

Two hooks keep the ## API Reference section of README.md in sync with the Python docstrings. Both run src/sync_docs.py.

HookDefined inTriggerWhat it does
Git pre-push hooks/pre-push.template, installed to .git/hooks/pre-push by sh install_hook.sh (run once per clone) Every git push Finds a Python interpreter (python, python3, then py) and runs src/sync_docs.py. If none is found it prints an error and exits 1, which blocks the push. Edit the template, not the installed copy.
Claude Code PostToolUse .claude/settings.json Every Claude Write or Edit tool call Runs python src/sync_docs.py so the README stays current during a Claude session. It fires on any file, not only .py files.
