Agentic SDLC Pipeline — Project Overview

The claude_capStone project: a set of Claude Code agents that take a Jira ticket (or a feature description) and drive it through requirements, design, implementation, review, testing and a pull request, with a human approving at the key gates. Start it with /run-orchestrator.

What this project is

A capstone project that automates the software development life cycle (SDLC) with Claude Code agents. One prompt, such as /run-orchestrator CLAUDE-4, runs a ticket through eight stages. Each stage is done by a specialist agent, and a developer approves the work at three gates before the pipeline continues.

Goals

  • Turn a Jira ticket into a reviewed pull request with a traceable paper trail of documents.
  • Keep a human in the loop: nothing past requirements, design review or the implementation plan proceeds without approval.
  • Keep roles separate: the agent that writes code does not write the tests, and the agent that writes tests never edits source to make them pass.
  • Report results exactly as observed, never a pass that was not run.

How the system is put together

The architecture is an orchestrator plus specialists pattern. A master agent coordinates; it does not write source code or tests itself. Specialists have narrow roles and a restricted tool list, and they exchange work through documents on disk.

Orchestration layer

sdlc-orchestrator plus the /run-orchestrator command.

  • Prints the 8-stage status board.
  • Invokes each specialist in order.
  • Enforces the approval gates and the HIGH/CRITICAL risk block.
  • Creates the feature branch and coordinates the commit, push and PR.

Specialist agents

Eight agents, one per SDLC stage.

  • Each has a small tool list (planning agents cannot run shell commands).
  • Only implementation-agent and verify-agent edit code files; only the implementer touches source.

Skills and rules

Shared know-how and policy.

  • Skills are loaded by agents for review checklists, PR templates and Jira calls.
  • Rules in .claude/rules/ are project instructions that every session follows.

Guardrails (hooks)

Scripts the Claude Code harness runs automatically.

  • Block destructive prompts and risky tool calls.
  • Run the unit tests after Python edits.
  • Keep the README API reference in sync.

Integrations

External systems reached through MCP.

  • Jira: pull the ticket, comment, transition.
  • GitHub (gh CLI): branch, push, PR.
  • Confluence is available through the Atlassian connector.

Document store

The shared memory between stages.

  • docs/<ticket-id-lowercase-no-dash>/, e.g. docs/claude4/.
  • Every document carries YAML front matter with its approval state.

  • Secrets are read from environment variables (ATLASSIAN_API_TOKEN, GITHUB_TOKEN), never stored in files.
  • .env.example documents the variables; copy it to .env.local (gitignored) and load it with scripts/setup-mcp-env.ps1 or .sh before starting Claude Code.

  • enableAllProjectMcpServers is on in settings.json.

Running the tests

python -m unittest discover -s tests

Tests add src/ to sys.path and import modules directly (e.g. from slugify import slugify); src/ and tests/ have no __init__.py.

How the pieces talk to each other

Agents do not share a conversation. They communicate through documents on disk and through messages passed by the orchestrator, which is the only party that talks to the developer.

Developer ↔ Orchestrator

  • The developer starts a run with /run-orchestrator <ticket>.
  • The orchestrator reports a summary and path at each gate and waits.
  • The developer replies approve or revise.

Orchestrator ↔ Specialists

  • The orchestrator starts each specialist with a brief and the paths of its input documents.
  • The specialist writes its output file and hands back a report.
  • That report is the agent's own words, not the developer's approval.

Specialist → Specialist

  • Indirect, through files in docs/<ticket>/.
  • Requirements feed architecture, which feeds design review, then the plan, then code, tests and the PR.
  • Numbered IDs (FR-N, RISK-NN, T-NN) let each document point back to its source.

Pipeline ↔ External systems

  • Jira over MCP: pull the ticket; post stage comments; transition to "In Review".
  • GitHub over gh: push the branch, open the PR, confirm with gh pr view.

Human-in-the-loop approval

Approval state lives in each document's front matter, so it is visible and auditable.

hitl_statusMeaning
pending-reviewWritten and waiting at a gate.
approvedA human approved. approved_by and approved_on are set.
revision-requestedA human asked for changes. The revised doc increases revision and returns to pending-review.
not-requiredNo gate (e.g. the architecture draft before its review).
Trust boundary. A document is marked approved only on the developer's own message. A specialist's report, a task notification or a relayed message is never treated as approval. In the CLAUDE-4 run, the orchestrator declined to act on a relayed approval until the main session recorded the developer's own words in the front matter.

Hand-offs when something is missing

  • If a subagent lacks a tool (for example Jira access), it stops and says so rather than guessing the ticket's content. The main session then fetches the data and passes it on.
  • Jira comments and transitions are done by the main session, which holds the Jira tools, when the developer asks.

Worked example: CLAUDE-4 — a slugify utility

Ticket: "Add a slugify utility to convert text into URL-safe slugs" (Task, Medium, label orchestrator-validation). A small, low-risk story chosen to validate the pipeline end to end. Six acceptance criteria: lowercase and trim, strip other characters, collapse spaces and hyphens, return an empty string when nothing is left, and raise TypeError for non-strings.

0. Start

/run-orchestrator printed the status board and asked for a ticket. The developer answered CLAUDE-4. The orchestrator could not reach Jira, so the main session fetched the ticket and passed its content on.

1. Requirements — approved

docs/claude4/requirements.md: 15 functional requirements, 7 non-functional and 10 constraints. It flagged assumptions for the developer to confirm, e.g. A-2: leading and trailing hyphens are stripped. The developer approved; front matter set to approved.

2. Architecture

New src/slugify.py exposing slugify(text: str) -> str using only re. Order of operations: type check, remove disallowed characters, collapse whitespace and hyphen runs, strip edge hyphens, lowercase. Six decision records and five known limitations.

3. Design review — approved

Six risks, none HIGH or CRITICAL, so Stage 4 was not blocked. One MEDIUM (assumptions still worded as open) was closed by the developer's approval; the rest were LOW (exact test imports, an implicit criterion-to-test mapping, a typo in a worked example, and two accepted limitations).

4. Implementation plan — approved

11 tasks (T-01 to T-11) touching only src/slugify.py and tests/test_slugify.py. It fixed the exact test imports, mapped every acceptance criterion to a test, and included a timing test for the performance requirement.

5. Implementation

The branch feature/claude-4-slugify was created from main, and implementation-agent wrote src/slugify.py with two precompiled ASCII regexes.

6. Code review

code-review-agent found 0 issues at any severity. That review was done by reading, not by running the code.

7. Verify

verify-agent wrote 20 tests in tests/test_slugify.py and found no source bugs. The full suite, re-run by the orchestrator: 84 run, 83 passed, 0 failed, 1 skipped. The skip is an existing placeholder from CLAUDE-2, not part of this ticket.

8. Pull request

pr-agent wrote docs/claude4/pr-description.md. One commit, feat: add slugify utility for URL-safe slugs (CLAUDE-4), with seven files staged by name. PR #5 was opened against main and confirmed open with gh pr view.

Summary

The project shows that a ticket can move from Jira to an open, reviewed pull request through a chain of narrowly scoped agents, with the developer deciding at the three points that matter most: what to build, whether the design is sound, and whether the plan is right to start coding.

What works well

  • Clear separation of duties: coordination, implementation, testing and review are done by different agents.
  • Traceable artefacts: every stage leaves a document with numbered items and an approval record.
  • Guardrails that run automatically: hooks block destructive prompts, secret edits and force-pushes, and re-run the tests after edits.
  • Honest reporting: test results and code-review scope are stated as observed, including what was skipped or only read.

Lessons from the CLAUDE-4 run

  • Subagents may not have every tool the main session has (Jira access was missing). The main session fills the gap and passes the data on.
  • Approval must come from the developer's own message. Relayed or automated notices are not approval, and the pipeline correctly refused to proceed on one.
  • Acceptance-criteria numbering should be copied from the ticket into the requirements, not inferred later.
  • Timing tests with fixed thresholds can be flaky on slow machines; changing one needs approval and a recorded waiver.

Possible next steps

  • Reproduce the Jira acceptance criteria verbatim in requirements.md.
  • Give the orchestrator access to the Jira tools so stage comments and the "In Review" transition happen inside the run.
  • Make sync_docs.py run only on Python edits to avoid unnecessary README churn.
  • Run the pipeline on a larger ticket to exercise the revision loop and the HIGH-risk block.
